# Logbook 全流程预检

本技能交付预检结论，不派发执行、不写目标、不改既有待办首行。发现卡点时的唯一动作是把它标成 🔮 待讨论项交人类裁决；人类解除标记前整本日志静止。

## 输入与前置条件

- 定位唯一目标日志并运行 `context --json` 与 `check --json`（见 [CLI 读取流程](../lb-update/references/document-adapters.md#本仓-cli-调用)），阅读原文。`preflight_clear` 为 false 时已存在卡点：先向人类汇总未决项，本轮不做新分析。
- 读取 [配置契约](../../docs/configuration.md) 解析本轮 documents；读取 [规划流程](../lb-plan/references/planning.md)、[协调契约](../../docs/coordination.md) 和 [证据模型](../../docs/evidence.md)。写回卡点前读取 [日志格式](../../docs/logbook-format.md) 与 [文档适配流程](../lb-update/references/document-adapters.md)。
- 三要素（工作目录、Stage 划分、待办清单）不全的日志先回 lb-plan 补齐，本技能不代写目标、不替人类新增待办。

## 必经流程

1. 路线规划：按文档顺序推导线性路径——Stage → 逐项待办 → 每项的技能链/子项/产物与验收口径 → 人工关口。`context` 的 `next_task` 只是解析候选，须结合原文核实；每步记录需要的结果、前序依赖、涉及仓库与技能、输入是否在场、验收如何证明。
2. 逐步可行性分析（fan-out）：每步派发一个只读分析 Agent，约束在该日志登记的工作目录内，核对——
   - 前序条件是否满足，依赖是否成立；
   - 步骤引用的仓库/机器/环境当前是否支撑（只读结构核验，不采业务证据、不运行业务命令）;
   - 步骤引用的技能与工具链在目标环境是否真实存在、可调用（不存在按能力缺口回报，不降级替代）；本机有 `skm` 时可用 `skm list --json` 辅助核对安装状态，没有 skm 不算卡点;
   - 验收证据可证明性：缺哪些数字、环境、门禁或凭据。
   每步的预期来自该步引用的 skill 本身：分析 Agent 应读取该 skill 的定义（SKILL.md 或目标仓库内等价物），按"skill 预期怎么工作 → 仓库/环境现实是什么 → gap 在哪"的对照输出，不满足于"技能存在/不存在"的清点。人工项只析前置条件。
   分析 Agent 一轮即回，只回传事实与缺口，不迭代、不修复、不创建产物。多步分析彼此独立时可并行派发；这属于只读核实，不是跨项执行并行。并发数按当前模型服务限额和宿主配置确定；限额未知时先小批次试运行，遇限流只重试失败路，不整轮重跑。只读分析在候选允许时选择不创建工作树的方案；敏感口径照旧只限内部候选。
3. 机读汇总：把结论写入所属项目 `sources/<主日志文件名>-preflight.md`（新生成或整文件幂等覆盖，不改动其他记录），结构固定：
   - frontmatter：`logbook`（主日志相对路径）、`preflight_date`（ISO 日期）、`overall`：`green`（全部 feasible）/ `amber`（有 needs-input 或 not-checked）/ `blocked`（有 needs-discussion 或 infeasible）；
   - **按待办拆分段落**：每个待办一节 H2（用待办原文做标题），节内依次为 `verdict:`、技能链、skill 预期、现场现实、gap（现实 vs 预期，逐项）、blocker（无则写"无"）、证据行号或路径；不加与待办无关的章节；
   - 未覆盖的步骤逐一列出原因，不能静默丢步。此文件是证据索引，不成为第二份任务清单；详细发现放对应 thinking，不复制正文。
4. 卡点回写：verdict 为 `needs-discussion` 的项，**先在对话中向人类展示卡点清单**，经其明确确认后，才把卡点写回主日志对应待办附近（预言球格式：`- [ ] 🔮 待讨论：<一句话> @<仓库>`，或作为缩进子项 `- [ ] 🔮 …`）。人类在对话中当场裁定并确认的卡点，记入 preflight 汇总与 thinking 即为解除，无需以 🔮 写回。写回不改目标、不改标题与待办首行、不勾任何框；写前重取 `version_token`，写后运行 `check --json`。回写动作本身不受已有 🔮 门禁限制（CLI 只拦 sync/task 写子命令），但同一轮也不得借此改写任何既有任务文字。
5. 收尾报告：展示计划位置、整体 verdict、逐步结论、卡点行号与解除条件；思考记录 preflight 日期、覆盖范围、未分析项及原因。结论是有时效的观察：全绿只表示「运行前预检未被阻塞」，运行态以 lb-push 派发时现场为准。

## 门禁语义（与 🔮 的契约）

- 🔮 表示「preflight 发现的待讨论项」：需要人类讨论裁决，裁决前整本日志不推进。任一待办或其缩进子项带 🔮 时，`bin/lb` 的 `sync`、`task update`、`task artifact`、`task add`、`task note` 一律以退出码 4 拒绝；`context --json` 报 `preflight_clear: false`，`check` 报 `PREFLIGHT_BLOCKER`。
- 解除方式只有一种：人在日志中亲手改写或移除 🔮（改写成普通待办、另行处理或删除），CLI 不提供绕过。preflight 技能自身也不改写人类待办首行。
- 🔮 不改变所属事项的验收语义，也不是 🚨（需人类负责人处理的计划外事项）或 ⏳（已到人工决定点）；它专指 preflight 产出的待讨论卡点，三者不互换。

## 回收与收尾

- 回收：每个分析 Agent 的结论必须全部取回（`herdr agent read` 或 Agent 落盘路径）并写入 `sources/<主日志名>-preflight.md` 之后，本技能的结果才算完整；任何 Agent 未回传、阻塞或超时都在预检档里如实记录为 not-checked 及原因，不静默丢弃。
- 卡点写回主日志前，须先在对话中向人类展示完整卡点清单，经其明确确认后方可写入；未确认前 🔮 不落盘。
- 采集到 Agent 输入行中未发送的用户文本时，按仓库规则视为用户意图信号：如实披露并按意图行动，不要求用户重发。
- 收尾动作：所有结论回收完毕后，关闭为本轮 preflight 创建的全部 Herdr 分析标签页（`herdr tab close`，仅限本技能创建的 tab），不让分析 Agent 残留为空闲会话；监控监听同样收掉，只清理本技能创建的标签页。若随后立即进入 lb-push 且复用分析会话为执行者，相应标签页移交为执行标签，由 lb-push 收尾时负责关闭。
- 分析 Agent 以 worktree 方式启动（如 `-w`）产生的残留工作树：只读核查后交所属仓库执行 Agent 或人类决定删除，协调者不跨仓清理。

## 边界

- 分析 Agent 只读、限定在已登记工作目录；数据敏感性按 [配置契约](../../docs/configuration.md) 的模型与部署规则选择，跨仓按最严格输入处理。
- 能力缺口（技能不存在、环境不可达、凭据缺失）如实回报 needs-input，不自行换工具或降级。
- 本技能不判断执行授权本身；获准与否由日志记载与 [AGENTS.md](../../AGENTS.md) 决定。预检通过不授权任何推进，推进仍须进入获准的 lb-push。
