# Return Alignment and Wrap-up

Read the [format](../../../docs/installable/logbook-format.md) and [coordination](../../../docs/installable/coordination.md) contracts before protected writes.

1. Re-read the current Logbook/Stage/task and authorization, including explicit human rulings. Keep concurrent human edits and original ownership.
2. Align the Sailor return: current package/task, result/revision, inputs/conditions, acceptance outcome, actual delivery entry, remaining responsibilities and limitations. Match identities within their object types: a run may use a differently named effective configuration, and neither identifier must equal the other or the package/session name. Require their reported association and compare each with the corresponding expected identity; differing run and configuration strings alone are not a mismatch. Business acceptance, tests and original observations are Sailor tasks. Captain verifies correspondence and readiness/control facts rather than rerunning business work. For business review sheets, do not compare original/repaired candidate rows, recount headers/table sizes or recompute layout budgets to produce a fresh pass. These are Sailor checks even when called return alignment; use the identified Sailor outcome or retain a gap.
3. Changed results, inputs or conditions invalidate affected conclusions until Sailor rechecks applicability. A new token, runtime idle/done/exit or bare completion claim proves no acceptance. Failed/incomplete/unknown/missing/conflicting returns leave the item incomplete. Reading or reconciling a failed return is coordination progress, not completion of the underlying acceptance task; do not silently redefine its endpoint as “the result was reviewed”. Only an explicit task criterion accepting a diagnostic outcome can establish that different endpoint. An update-only request launches no investigation or rework. For a recovery claim, record the actual side effect, the available before-state or equivalent evidence, and the exact recovery scope in the existing task or bound Thinking. Without that evidence, retain an explicit unverified recovery gap. With sufficient evidence, record only the supported restored scope and its evidence pointer; a completed task checkbox alone must not hide that limitation or imply the entire environment was restored.
4. Required independent checks use another Sailor on the same candidate and retain finite rounds. Do not create an acceptance role or default extra checker. Existing execution authorization covers routine rework; scope changes and human gates need the applicable Admiral decision.
5. Protect human items: only actual human work starting may be recorded as `[ ] → [/]`; do not complete/cancel/revert them. An explicit skip ruling may disposition an existing skipped agent task without claiming successful delivery.
6. Apply the [delivery contract](../../../docs/installable/coordination.md#human-deliveryreadiness--us4): align the owning Sailor's inventory/binding outcome and current PR or branch/candidate entry. Missing checks or a stale/inaccessible entry leave delivery incomplete. Persist the gap in the existing delivery task: identify the current candidate and owning Sailor, the missing complete-inventory and binding/index checks, and the return needed to resolve them. Merely listing excluded files or saying “layout check missing” does not specify the required follow-up. An update-only request records this outstanding responsibility without sending it, launching repair, untracking files or cleaning up; existing human annotations and recovery pointers remain intact.

7. Preserve useful decisions/recovery in existing bound Thinking and host-owned business records. No mandatory source index, raw-output archive, file-per-return or copied business content is required. Preserve human comments and avoid cleanup that destroys their recovery pointers.
8. Write only minimal authorized progress through [the document workflow](document-adapters.md), inspecting the diff and using the returned token for sync/check. Close distinguishes achieved goals, accepted deviations, cancellations, open responsibilities and actual human rulings; it creates no extra human gate.

Report actual writes, applicable return identities, outstanding gaps and the next owner. Cleanup is separately authorized.

Keep one concise current status for each identified candidate instead of appending contradictory historical blockers. Use a local document-adapter edit when the CLI has no matching status replacement operation; inspect the current bytes and protected diff. Preserve dated candidate history in existing Thinking, human comments and recovery pointers. Separate a locally repaired/trial candidate from published assets. Preserve human checkbox decisions; if platform observations differ, state the specific object, observation time and discrepancy without reverting the human item or generalizing one PR result to other PRs. Keep review sessions available until the agreed human reception and authorized cleanup.

## Requested run metrics

Record run start/end/resume, human waiting/interruption, distinct human turns and applicable first acceptance/corrections in the existing bound Thinking using the [event contract](../../../docs/installable/coordination.md#run-event-and-close-out-metrics). Resume keeps the same run and counters. Captain records coordination facts; Sailor returns actual acceptance facts and later defect corrections. Do not archive raw trials or create a metrics sidecar.

At Stage/logbook 🎉, report exact scope, wall elapsed with waiting/interruption union, human interaction count/categories and first-pass numerator/denominator/rate. Use the read-only `skills/lb-push/scripts/run-metrics.py` helper for deterministic arithmetic; no event history or zero denominator gives explicit unknown/no-calculable-data, never invented success. A corrected delivery defect removes an erroneous first-pass pass even if rework later succeeds. Metrics do not complete human gates or create a checker role.
