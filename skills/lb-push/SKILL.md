# Advance Project Tasks

The mode is advance, resume, or cleanup (release approved resources). Advancement not limited to a single item runs serially along the confirmed list; an explicit single item or batch respects its endpoint. Mode or skill switching never expands authorization.

## Inputs and Preconditions

On every invocation, first read the target logbook from disk and verify goals, non-goals, working directories, the complete ordered list, authorization, and existing report-backs; never substitute session memory or stale line numbers. Must read the [Configuration Contract](../../docs/configuration.md) (including collaboration parameters), [Execution and Recovery](references/execution.md), and the [Coordination Contract](../../docs/coordination.md). Consult the human when a parameter required by this step is missing and read-only verification cannot fill the gap.

When creating or replacing a session, parse the full launcher; even when reusing, verify the actual model, deployment, and input boundaries. Runtime operations determine runtime.adapter and its actual capabilities; before controlling Herdr, read the [Herdr Adapter](references/herdr.md) and the environment's tool skill. When a capability is missing, stop the dependent step; do not bypass wrapper, monitoring, or isolation requirements.

Before writing, read the [Logbook Format](../../docs/logbook-format.md) and the [Document Adapter Process](../lb-update/references/document-adapters.md). Maintain only the approved list, statuses, and short facts; preserve human goals, large prose bodies, and existing heading wording and numbering.

Never rewrite, append to, or trim the first-line text of existing todos; update checkbox status only from evidence. Under a task, add only minimal status, blockers, or artifact links; execution process, technical details, and detailed evidence go into the corresponding Thinking, not piled into main-logbook sub-items.

## Advancement Loop

When dispatching, reusing, or waiting for report-backs, watch the execution session's context usage. Above 80%, run GC automatically without re-confirmation: save the work package, worktree, candidates, evidence, open responsibilities, and unsent inputs; end the old session at a safe boundary; start a new session with a compliant wrapper, continue in the original worktree, and rebuild monitoring. Do not inherit the old context wholesale, and do not wait for `/compact` instead of GC. When the old session cannot provide a handoff, recover from the verified logbook and disk state, first reconciling unfinished operations to avoid duplicate side effects. Keep uncommitted changes and services still in use; do not delete the worktree; do not reset acceptance or review counts. Never guess when usage is unknown; reclaim only execution sessions this project is authorized to manage. When entering from lb-status, only perform the GC — resume the original task only if it still carries execution authorization; do not dispatch a new task.

Browser work goes to the executor agent using the host-declared browser tools with a task-scoped session; when a pinned profile is needed, read `browser.profile` from `lbkit-agents.yaml`, and consult the human when it is missing and cannot be inferred from the task. Verify browser ownership at dispatch and acceptance; a session name alone is not proof. Never connect to or take over the human's main browser, never delete locks or close user windows; when the profile is occupied, report the conflict instead of force-reusing. Logins are completed by the human in an automation-dedicated browser.

1. Following the [CLI Reading Process](../lb-update/references/document-adapters.md#本仓-cli-调用), run `context --json` on the current logbook and verify the first item against the original text and authorization; never trust `next_task` alone. advance selects the first unchecked item in document order; resume verifies the original package, current list, and authorization. Resume an existing executor of the same package instead of re-dispatching; a blocked first item is not skipped. When the plan is human-confirmed and inputs are ready, dispatch proactively — do not stall at "ready to start". New or restructured plans must satisfy the lb-plan exit criteria: human goals authored, and working directories, Stages, and item-by-item todos confirmed.
2. Verify the work package's result, scope, inputs, owner, dependencies, evidence gates, and any required finite review rounds. Missing facts within authorization are investigated by the owning agent; consult the human for out-of-scope information. When an evidence gate requires E2E, a real environment, quality reports, or key-step screenshots, never downgrade it to a static check; see the [Evidence Model](../../docs/evidence.md) for detailed evidence requirements.
3. Filter the declared launcher options by input sensitivity, then choose a model per the task's needs. Sensitive inputs, or inputs of unknown classification, go only to confirmed internal deployments; the same applies to reuse, sub-agents, and evaluations. Dispatch the full work package in the responsible repository through the selected runtime adapter; business execution uses an isolated worktree. Reuse sessions when model and context fit; split when independent checks or approved parallelism are needed. The coordinator does not do cross-repo implementation or environment setup on the agent's behalf.
4. Verify the full task was received and observe actual execution. After receipt, mark `[/]` via CLI `task update --status /`, re-fetch context/token, then sync the stage status with `sync` — preview the diff before writing and run `check` after; a trust gate or an empty tab does not mean receipt. Confirm a visible read-only monitoring session tied to this dispatch exists; the model decides whether to create or reuse one. If monitoring fails, fix the original monitoring rather than re-dispatching. Workspace, naming, focus, and safe argument passing follow the Herdr adapter.
5. After waiting, read the latest status and output. `idle`, `done`, or `blocked` triggers report-back or blocker verification — never a direct checkbox tick; while still `working`, judge progress from new facts. A single wait is bounded by limits.wait_seconds; usually 10 consecutive minutes without effective progress reaches the stalled limit — judge per the task's nature, and never drag on with repeated waits or session restarts. At the limit, verify the scene, stop retrying, and report; never kill the process just because a wait expired.
6. Execution deviating from the confirmed plan can be corrected within the original scope; when the confirmed plan itself is wrong in direction, on major decisions, on out-of-authorization key information, on login approvals, or on scope changes, stop and consult the human. Handle routine issues within the original task yourself; do not bounce work the owning agent could complete back to the user. When candidates, samples, tools, or environments are missing, do not substitute a report full of "unknowns" for the original deliverable; keep the received item at `[/]` and record the blocker per the facts.
7. Report-backs must be verified and written back via [lb-update](../lb-update/SKILL.md), preserving the review rounds already used. After acceptance passes, re-read the original text and `context`, then continue to the next item within the existing advancement authorization; stop at an explicit single-item/batch endpoint, a human gate, a severe blocker, or full completion. New items, reorderings, and scope expansions still require human decision — continuous advancement is not a license to overstep.

External publishing follows host rules: verify the authenticated identity belongs to the human owner, and write the body in their judgment and voice — never cast a coordinator or executor agent as the externally accountable party. Pause the publication when identity or voice is unclear; a tooling capability gap does not authorize switching to a semantically different channel.

cleanup touches only approved resources; it does not pick a business first item or dispatch follow-up tasks. Deleting a completed worktree falls under the root-rule exception; reuse, retention, and cleanup of sessions and monitoring are judged by the model against the scene, without affecting other projects.

## Reporting and Handoff

Choose the form of key-result handoff by audience: artifact lines under todos prefer local paths the human owner can actually access; use remote URLs only when the file does not exist locally or must be shared across machines or externally. Web-type results such as work items, PRs, and published single-page HTML still use URLs and are written into the owning phase's related links section. Before writing back, verify the link or path corresponds to a deliverable that actually exists; label unpublished or unarchived material truthfully, keep existing evidence locations, never treat a rewritten path as completed archival, and do not add publish or archive tasks on your own because of this requirement.

Report receipt facts, the executor's location (Herdr name, workspace, tab/pane), monitoring, results or blockers, and who does what next and when it resumes; do not report focus. Separate operational facts from acceptance conclusions; no report-back never implies completion.

When a human must take over, re-read the logbook before replying to get accurate file and line numbers, and state the verified facts, attempted approaches, possible decisions, and unblock conditions. For logins or approvals, give the specific system, object, page or session location, and the completion marker; for major decisions, explain the tradeoffs. When facts are insufficient, fill them in within authorization first — do not make the user explore blindly. For any out-of-plan matter that needs the human owner and cannot advance, write `🚨` plus the blocker cause, the concrete action, and the unblock condition at the very front of the item body, keeping the original status (received items stay `[/]` — no ticking, no adding or moving tasks; human-owned items must not be changed to in-progress); conversational reporting does not substitute for a logbook write-back. Human todos already marked `👱` in the plan just stop at the gate — do not add `🚨`; blockers an executor is handling itself await its report-back and escalate to `🚨` only when stalled past the limit or out of bounds.

When no human takeover is needed, state the owning agent's next action and report-back conditions, and continue authorized work without turning a progress report into task-level confirmation. At the authorization endpoint, state clearly what was completed and what the next item is; do not start it on your own.
