# Herdr Operating Conventions

This file applies only to runtime.adapter=herdr. Before performing Herdr operations, read this file and the environment's Herdr tool skill, and verify available parameters against the current interface; do not load its CLI details when this adapter is not selected. Authorization and execution isolation are defined by [AGENTS.md](../../../AGENTS.md).

## Launch and Isolation

The control scope is the current workspace and authorized sessions. Business execution packages are operated by the owning agent in an independent Git worktree under the original repository; deleting a completed worktree falls under the root rule's cleanup exception; the coordinator must not do cross-repo worktree setup or business environment provisioning on the agent's behalf. If no owning agent capable of that setup exists, report the prerequisite instead of bypassing the boundary.

The executor agent uses a dedicated tab distinct from the coordinator's main tab and keeps its working directory. Create with `--no-focus`; background operations must explicitly target the agent, tab, or pane. Operations that cannot avoid stealing focus are left to the human.

Local sub-agents dispatched by the logbook must be created in the coordinator's current Herdr workspace. Before creating a tab, read `runtime.herdr.workspace_id_env` from the host's `lbkit-agents.yaml`, get the environment variable's actual value, and pass `--workspace <值>` explicitly; consult the human when it is missing and read-only verification cannot fill the gap — never rely on the TUI's current focus. One repository usually keeps one applicable agent session; consecutive work packages prefer resuming and reusing it; do not create a session per task. Create another only when independent checks require implementer isolation, the existing context or model/data boundary no longer fits, or a user-approved parallel batch genuinely needs an independent executor — and record the reason in the handoff. Even when reusing, verify the actual model, deployment, working directory, open responsibilities, and current-task compatibility.

All Herdr named sessions, tab labels, and pane labels created by the logbook use `runtime.herdr.label_prefix` from the host's `lbkit-agents.yaml`; the template default is `^`, so humans can tell agent-created resources apart. This applies to execution, monitoring, and temporary gate panes alike. Immediately after creation, verify the actual label; if naming failed, fix the original resource rather than duplicating a same-purpose resource. Herdr agent identifiers are constrained by the tool's own format — do not force the label prefix onto them; still use a stable, unique, locatable agent name.

Agents the human needs to watch may keep status markers. Internal infrastructure needing isolated visibility should run in an authorized separate workspace or named session; do not assume hidden status just because the name is cleared. Report a blocker when the required layout is missing — never cram it into the main pane. Visible monitoring for every execution package must still satisfy the root rules.

Launch selection comes from the host's `lbkit-agents.yaml`; explicit user choices only take effect within the candidate range. Filter by sensitivity first, then choose a model per task needs; record the option and deployment rationale. Parse this round's runtime parameters per the [Configuration Contract](../../../docs/configuration.md); configuration does not authorize other repositories, publishing, or modification. Never infer engine or permissions from a default wrapper command's name — inspect the actual process.

Dispatch the executor agent with the full wrapper command and parameters declared in the host's `lbkit-agents.yaml`; never substitute `herdr agent start --kind`'s generic engine. If the wrapper is a shell function, verify it exists in the target interactive shell per `runtime.herdr.shell`, then launch per the current Herdr interface; report the gap if it cannot be found. After launch, verify the actual model and deployment ownership, then name, hand over the package, and monitor. When deleting a completed worktree, a declared no-worktree launch option may be used; that does not authorize branch deletion, fetch, or other Git management operations.

Actual launch sequence when the wrapper is a shell function (verified 2026-10-09): `herdr tab create --workspace <ws> --cwd <仓库根> --label '<前缀> <名>' --no-focus` creates a shell pane; `herdr pane run <pane> '<函数名>'` starts the wrapper inside that interactive shell (`pane run` delivers verbatim, no expansion); then `herdr agent rename <pane-id> <名>` names it (rename accepts a pane id as target; any unoccupied name works); `herdr agent read --source visible` reads the TUI footer to verify the actual model; finally `herdr agent prompt` hands over the package. The coordinator handles two common codex-family launch dialogs: for the background daemon's feature-settings conflict choose 「Run without daemon this time」 (do not change shared settings); for the weekly-rate-limit model-switch suggestion choose 「Keep current model (never show again)」 — the weekly quota is an account-level shared pool, switching models saves nothing, and the option exists only to stop the interruptions.

The coordinator handles repository trust gates per the root rules: after confirming the dialog's path is a logbook-registered repository authorized for the current task, or a legitimate worktree of one, accept workspace trust by default and retry the original wrapper launch; never auto-accept unregistered or unknown paths. Passing trust only clears the launch gate — it does not mean the business package was received, nor does it expand login or approval permissions.

## Permission Modes

Whether auto-approve is used is governed by host rules and `runtime.herdr.permission_mode`; consult the human when authorization or parameters are missing — do not pick an approval mode yourself. This never permits leaking secrets, destructive data operations, cross-scope access, or unauthorized commits, pushes, merges, or publications; switching agents must not be used to dodge upstream restrictions or real-identity approval.

- On resume, still use the selected wrapper option and verify session identity; never bypass model selection with a bare engine command; new sessions must not unconditionally restore old context.
- A tool supporting some kind does not put it in the repository's candidate range. Never treat a generic-engine example as a launch option or replace the selected wrapper command with an engine command; never change model, profile, or deployment ownership via extra parameters.
- Before dispatch, check the actual model matches the selected deployment option and inspect process parameters; an approved permission mode also needs actual status evidence. Merely toggling the UI mode is not evidence. When the actual parameters of the wrapper launcher lack evidence, report unverified — never assume the requirements are met.
- If only the launch parameters do not match the authorized mode, save the handoff, fix it in the same dedicated tab, and resume; do not repeatedly click single approvals. On a real login, approval, or upstream rejection, hand it straight to the human.

Record durable permission agreements once in thinking when necessary; never copy transient approval prompts into the main logbook.

## Dispatch and Monitoring

When submitting a work package via `herdr agent prompt`, pass the full task text as a single literal argv parameter. Never insert text containing Markdown backticks, `$()`, or other shell-active content into an unquoted or double-quoted shell command string; prefer the direct interface or single-quote/argv passing that preserves literal content. When shell rewriting is a risk, read back the actual prompt after submission and verify verbatim that nothing was executed, expanded, or truncated.

Before sending, verify the target workspace, tab/pane, actual session, and input line; one pane may have switched between main and side sessions, so the name and pane ID do not prove the recipient's identity. Notifying a Captain must be confirmed by its actual main session; side-session receipt or a tool-reported agent_prompted only proves local delivery. When the input line holds unsent residual text, `herdr agent prompt` overwrites the residue with this submission without concatenating — always use `agent prompt` for submission and line clearing; `agent send-keys`' enter/esc/ctrl+u/backspace do not work on the codefuse main input line, so never submit or clear via keystrokes (verified 2026-10-01).

When the target is in a side session, first verify the main session's status, unsent input, and the switch method the current UI supports; switch back only within the authorized control scope and only when it will not interrupt a run, overwrite input, or steal focus, then read back the identity and send. Never hardcode shortcuts, and never guess delivery by repeatedly messaging. A side session's tool limits must not be generalized into the whole project having no execution ability, nor bypassed by switching sessions; when it cannot be done safely, clearly report that the main session has not yet acknowledged. Logbook migration notices must include old/new entry points, the report-back location, unchanged responsibilities, and the re-read-before-write requirement; record the handoff after the main session confirms. When unsent input exists, the main session's state is unknown, or the control plane explicitly forbids it, only read-only verification is allowed; never probe limits by trial-switching or trial-sending — tool interception is no substitute for pre-send judgment.

After submitting the full work package, confirm the actual task text is visible or an explicit confirmation arrived, then observe the agent's real status. Trust, authentication, or other launch gates are not business execution; report the concrete gate, and never imply work in progress with an empty tab.

After the work package is received, confirm there is an independent, visible, read-only monitoring tab in the executor's workspace, using Herdr's status-wait mechanism to watch the designated agent for `idle`, `done`, or `blocked`. The model decides whether to create or reuse; reconfirm the association and monitoring readiness on resume and package change. Monitoring tab/pane labels also use the host-declared prefix. Monitoring must be tied to this dispatch — leftover idle from the previous round is not this round's completion.

Monitoring does not enter repositories, run business commands, replace acceptance, or answer approvals. It only lets the human see status changes and the report-back location, then hands off to the coordinator for verification. Occasional status queries are for diagnosis only and must never be claimed as started monitoring.

Operations requiring the human's own terminal action (sudo, passwords, system authorization, etc.) never go into agent sessions: create a separate plain terminal tab as needed (no agent; label with the host prefix), use `pane run` only to echo static instructions (template commands, todo lists), and run no business commands; once the human is present, `pane send-text` may prefill the exact command into the input line (without a newline) so the human just presses Enter. When an executor agent's task involves such operations, stop and list the exact commands, then verify read-only afterwards.

The coordinator must verify monitoring is actually running and read this round's status and new output — never just create an empty tab. Use the tool's currently supported status wait, e.g. `herdr agent wait <agent-name> --until idle --until done --until blocked --timeout <毫秒>`, with each wait at most `limits.wait_seconds × 1000`. Existing visible monitoring results are available for the coordinator to use; do not force repeated waits over Codex vs Claude Code client differences. Two field-tested traps: when an executor has a background task running (polling/long command), its status shows idle between turns — one `agent wait` return only proves the turn ended, not completion; the completion criterion is new execution output or an explicit report-back. Conditional monitoring via grep text matching on pane content will hit the prompt's echoed original text — condition on incremental signatures such as "newly appeared output lines", or switch to status waiting and direct reads. Once confirmed the executor advances via background tasks, abandon pure idle polling (every between-turn gap hits immediately, wasting waits); instead re-read pane output on a schedule and spot-check on-site side effects (artifact files, download rate, CPU) to judge progress. Wait expiry only refreshes the observation; task stalling and timeouts are judged per [Execution and Recovery](execution.md).

When dispatch succeeded but monitoring failed, accurately report partial completion, keep the task and agent identifiers, fix the authorized monitoring step, and do not re-dispatch. After a one-shot monitoring ends, reconfirm monitoring readiness when resuming the same package. Waits use limits.wait_seconds; stalling is handled per [Execution and Recovery](execution.md); never fabricate unverified monitoring commands.

## Retention, Recovery, and Closure

Release conditions after normal completion: deliverables and evidence archived, required checks passed or explicitly unnecessary, remaining gaps reported back, no open responsibilities, and the session context no longer worth retaining.

Completing a work package does not force closing the session. Retain when the context, ongoing investigation, or follow-up work still has value, recording the reason and recovery triggers; use status values the tool actually supports. Do not retain without reason, and do not silently expand a completed work package. When the previous skill (e.g. lb-preflight) just did read-only analysis in the same repository and its session is still idle, prefer reusing that session as the executor: it already carries the repository and skill-chain context, so dispatch continues seamlessly without a new session or re-briefing (verify model, deployment, and data boundary as usual before reuse).

When the user requests termination, cleanup, or resource constraints force an abnormal shutdown, first preserve the handoff, open responsibilities, and recovery conditions, then close within authorization; never record an abnormal closure as accepted completion. Managing a group of agents is not managing every service; confirm ownership and operation permissions for old services.

When actively ending an execution session (GC), note: an executor agent cannot send `/exit` or other user-side built-in commands to its own CLI — writing the command into its reply text does not mean it executed. The coordinator sends `/exit`; when the input line holds unsent residual text, submit via `herdr agent prompt` (it overwrites the residue), never concatenated with `pane run`. When a `-w` worktree session exits, a 「Keep / Remove worktree」 dialog pops up with Keep preselected: GC rules require not deleting the worktree, so confirm the cursor is really on Keep before pressing Enter; if the meaning is unclear or Remove is preselected, do not blind-confirm — press Esc to cancel and hand to the human. Before exiting, have the executor write out and push the handoff, uncommitted changes, and recovery conditions; after exit, record recovery leads (the CLI echoes a `--worktree <名> --resume` recovery command in the pane). When artifact lines pointed to paths inside that worktree, migrate the artifacts to a stable location or repoint the artifact lines to an immutable identity before deletion.
